# Clients Management App

Frontend часть тестового задания: SPA для управления базой клиентов (Backoffice style).

## 🚀 Быстрый старт

### Требования
- Node.js 18+
- Запущенный Backend API (FastAPI)

### 1. Настройка окружения
Убедитесь, что бэкенд запущен и доступен.
Скопируйте файл конфигурации:
```bash
cp .env.example .env
```
При необходимости отредактируйте `.env`, указав актуальный API URL.

### 2. Запуск приложения
```bash
# Установка зависимостей
npm install

# Запуск в режиме разработки
npm run dev
```
Приложение откроется на: `http://localhost:5173`

## 🏗 Архитектура и Ключевые решения

Проект построен на принципах **Feature Sliced Design** (в рамках одной фичи `clients`) с акцентом на **Single Source of Truth** и разделение ответственности стейта.

### 1. Управление состоянием (Data Flow)

Мы осознанно отказались от глобальных сторов (Redux, Zustand) для бизнес-данных в пользу специализированных инструментов:

| Тип стейта | Инструмент | Обоснование |
| :--- | :--- | :--- |
| **URL State** | `react-router-dom` | **Single Source of Truth** для фильтров, пагинации и сортировки. Позволяет шерить ссылки, использовать историю браузера и избегать рассинхрона между UI и URL. |
| **Server State** | `TanStack Query` | Управление асинхронными данными, кэширование, дедупликация запросов и автоматическая ревалидация. |
| **UI State** | `useState` / `React Hook Form` | Локальное состояние компонентов (формы, модалки, дебаунс инпутов), которое не нужно шарить глобально. |

### 2. Оптимизация

*   **Clean URL**: В URL попадают только параметры, отличающиеся от дефолтных. Ссылка остается читаемой (`?query=АО`), а не перегруженной техническими параметрами.
*   **Debounce**: Поиск по тексту обновляет URL (и триггерит запрос) только после завершения ввода (500ms).
*   **Smart Selects**:
    *   *Регионы*: Загружаются один раз и кэшируются (staleTime).
    *   *Родители*: Загружаются "лениво" (Lazy) только при открытии селекта, чтобы не грузить лишние данные на старте.
*   **Strict Typing**: Используется единый источник типов `PARTY_TYPES` (as const) для синхронизации значений между TypeScript, валидацией (Zod) и UI.

## 💬 Ответы на вопросы из ТЗ

> **Как другие компоненты будут получать обновления из store?**

В данной архитектуре "классический store" отсутствует. Компоненты получают данные через хуки:
*   Данные списка: `useClients(filters)` (под капотом React Query подписка).
*   Состояние фильтров: `useClientsFilters()` (под капотом подписка на URLSearchParams).
Это обеспечивает автоматическую реактивность: изменился URL -> обновился хук фильтров -> React Query увидел новые фильтры -> перезапросил данные -> обновился UI.

> **Какой вариант вы считаете оптимальным для данной фичи и почему?**

Связка **React Query + URL Params**.
Для CRUD-приложений (списки, таблицы) состояние почти всегда равно "параметры запроса + данные сервера". Хранить это в Redux — создавать лишний бойлерплейт и риск рассинхронизации. Выбранный подход минимизирует код и сложность поддержки.

> **Обновление списка после create/edit?**

Выбрана стратегия **Invalidation** (`invalidateQueries`).
Хотя ручное обновление кэша ("Optimistic UI") работает быстрее, в таблицах с пагинацией, серверной сортировкой и фильтрацией крайне сложно предсказать, куда именно должен "встать" новый или измененный элемент. Инвалидация гарантирует 100% консистентность данных с сервером.

## 🛠 Технический стек

*   **Core**: React 19, TypeScript, Vite
*   **Routing**: React Router DOM v7
*   **Data Fetching**: TanStack Query v5
*   **UI Kit**: Material UI (MUI) v7
*   **Forms**: React Hook Form + Zod
*   **Code Quality**: ESLint, Prettier

## 📂 Структура фичи (`src/features/clients/`)

```
src/features/clients/
├── components/          # UI: Таблица, Фильтры, Модалки
├── hooks/               # Логика: useClientsFilters (URL sync)
├── pages/               # Страница раздела (сборка компонентов)
├── services/            # API: React Query хуки (useClients, useUpdateClient...)
└── types/               # Типы: DTO, Interfaces, Enums
```
